## 0. サマリ

午後Ⅰの解答入力後、自己採点（○/△/×）していた部分を **AI が自動採点**し、
行ごとに「何が足りないか」「どう書けば点になるか」を示し、
**失点の型を分類して次にやるべきことを提示する**機能を追加する。

本アプリ初の**サーバサイド処理**（Vercel Functions）が必要になる。
LocalStorage のみ・バックエンド無しという前提が変わるため、要件を先に固める。

## 1. 解決したい課題

対象: 実務経験の浅いインフラエンジニア1名（PM試験受験者）。午後Ⅰの得点が最優先。

現状の演習フローは `解答入力 → 答え合わせ → 自己採点(○/△/×) → 記録` だが、
記述式の自己採点には初学者には越えられない壁が3つある。

| # | 課題 | 具体例 |
|---|---|---|
| C1 | **判定できない** | 模範解答と文言が違うとき、正解なのか失点なのか自分では判断できない。甘くも辛くもなり、点数が実力を表さない |
| C2 | **自分の解答のどこがダメか分からない** | 既存の解説は「なぜこの模範解答になるか」は書いてあるが、「**あなたの解答**に何が欠けているか」は書いていない |
| C3 | **次に何をすればいいか分からない** | 失点が「題意を外した」のか「本文の根拠を拾えなかった」のか「字数に要素を詰められなかった」のか分類されないので、対策が立たない |

**C3 が本丸。** 点数を上げるのは採点精度ではなく、失点パターンの特定と是正。
C1・C2 はそのための手段と位置づける。

## 2. スコープ

### やること

- 午後Ⅰ解答入力画面（`/afternoon/answers/:id/myAnswer`）での AI 自動採点
- 行（設問）ごとの判定・不足要素・**書き直し例**の提示
- 失点タイプの分類（§5.3 の分類表）
- 1回の演習に対する総合アドバイス（強み・弱み・次にやること）
- 過去の演習を横断した**弱点プロファイル**と推移（フェーズ4）
- AI 採点失敗時の、既存の手動自己採点へのフォールバック

### やらないこと（スコープ外）

| 項目 | 理由 |
|---|---|
| 午後Ⅱ（論述）の自動採点 | 引継ぎ §8 で明示的にスコープ外。本件で作る基盤は将来転用できるが、今回は手を出さない |
| 問題本文（IPA原文）のアプリ内収録 | 著作権。§5.1 のとおり**本文なしで採点が成立する**設計にする |
| AI 採点結果を確認なしで XP・バッジへ直結 | 誤採点が学習履歴を汚染する。§4.4 のとおり必ず利用者確認を挟む |
| オフラインでの AI 採点 | 原理的に不可。PWA では「採点できません」と明示し手動採点に倒す |
| 複数ユーザ対応・アカウントごとの課金 | 対象ユーザ1名 |

## 3. 現状の整理（既存資産の棚卸し）

調査の結果、**採点に必要なデータは全問そろっている**。

| データ | ファイル | 充足状況 |
|---|---|---|
| 問題メタ | `data/afternoonProblems.ts` | 37問 |
| 公式解答例 | `data/officialAnswers.ts` | **37問すべて** |
| 配点 | `data/scoringMap.ts` | **37問すべて**（行ごとに `{correct, partial}`） |
| 公式設問文（IPA原文） | `data/afternoonQuestionTexts/` | **全12年度・296行**。`rowKey` で解答行と1:1 |
| 独自解説（行ごと） | `data/afternoonExplanations.ts` | **37問すべて**。`point` / `basis` / `reasoning` / `pitfall` |
| 詳細解説（本文セクション解説） | 同上 `detail.problemSections` | **37問すべて** |

行の対応キーは `rowKey = "${s}|${q ?? ''}|${t ?? ''}"`（例 `1|(1)|`）で全データ共通。
利用者解答のキーは `officialAnswers.answers` の**配列インデックス文字列**（`"0"`, `"1"`, …）。
この2つの変換が必要（`processRows` の `rowIndex` が橋渡しになる）。

**既存の採点フロー**（`pages/AfternoonMyAnswer.tsx`）:

```
myAnswers {rowIndex: string} → checkMode → scorings {rowIndex: 'correct'|'partial'|'wrong'}
  → calculatedScore = Σ scoringMap[id][rowIndex][judgment]
  → 全行マーク完了で「記録」活性化
  → addRecord() + applyAfternoonRecord() + addActivityEvent() + saveSavedAnswerSnapshot()
```

**AI 採点はこの `scorings` を埋める手段として差し込む。** 下流（点数計算・記録・XP・同期）は一切変えない。
これが最小の変更で最大の効果を得る接続点。

## 4. 機能要件

### F1. 採点の実行

- 答え合わせモードに「**AIに採点してもらう**」ボタンを置く
- 未入力行があっても実行可（空欄は `wrong` 相当として扱い、その旨を返す）
- 実行中は行ごとの進捗ではなく全体のローディングを出す（処理は1リクエスト）
- 所要時間の目安を表示する（§8 の実測後に確定）
- 二重実行を防ぐ。実行後は再実行ボタンに切り替える

### F2. 行ごとのフィードバック

各解答行に対して以下を表示する。

| 項目 | 内容 | 表示 |
|---|---|---|
| 判定 | ○ / △ / × と獲得点 | 行ヘッダ |
| 確信度 | high / low。low のときは「要確認」バッジ | 判定の隣 |
| 一言講評 | 40字以内。何が良く/足りないか | 常時表示 |
| 不足要素 | 模範解答が持っていて利用者解答に無い要素（箇条書き） | 常時表示 |
| 失点タイプ | §5.3 の分類（複数可） | タグ表示 |
| **書き直し例** | **利用者自身の解答を活かして**字数条件内で満点になるよう直したもの | 折り畳み |

**書き直し例が学習効果の核。** 模範解答をもう一度見せるのではなく、
「あなたの書いた文をこう直せば点になる」を見せることで、次回の書き方が変わる。

### F3. 総合アドバイス

1回の演習全体に対して:

- **できていたこと**（1〜2点。伸ばす部分を明示）
- **崩れていたこと**（1〜3点。失点タイプの集計に基づく）
- **次にやること**（2〜3件。具体的な行動。「〇〇年度問△をもう一度」「設問を読んだら条件に線を引く」など）

### F4. 採点結果の確定（利用者確認必須）

- AI の判定は `scorings` に**プリセットされるが確定ではない**
- 利用者は任意の行の ○/△/× を上書きできる（既存 UI がそのまま使える）
- 「記録」を押した時点の `scorings` が正。AI が勝手に記録・加点することはない
- AI 判定と利用者の最終判定が食い違った行は保存しておく（§7 の `userOverrode`）→ AI 採点の信頼度を後から検証できる

> **これは安全装置であると同時に学習装置でもある。** AI の判定根拠を読んで「いや自分は合っていた」と
> 判断する行為そのものが、採点基準の内面化につながる。

### F5. 弱点プロファイル（フェーズ4）

- 過去の全演習の失点タイプを集計し、`/afternoon` に「あなたの失点の傾向」として表示
- 直近5回と全期間を比較して、改善しているタイプ／していないタイプを出す
- 特定タイプが突出しているとき、対応するノート（`/notes/afternoon-tips` 等）へ誘導する

### F6. フォールバックとエラー処理

| 状況 | 挙動 |
|---|---|
| オフライン | ボタンを不活性化し「オフラインのため手動採点をお使いください」 |
| API エラー・タイムアウト | エラー文言＋再試行ボタン。手動採点は常に可能なまま |
| 採点キー未設定 | 設定画面へ誘導 |
| レスポンスが壊れている | 部分的にでも読める行は反映し、残りは手動採点に倒す |

**どの失敗経路でも、既存の手動自己採点が必ず使えること。** これは必須要件。

## 5. 採点の設計

### 5.1 AI に渡す情報（問題本文なしで成立させる）

問題本文（IPA原文）はアプリに無く、著作権上も収録しない。
代わりに以下を渡す。**採点は「利用者解答 vs 模範解答＋採点基準」の照合**であり、
本文の再読解ではないので、これで成立する。

| # | 渡すもの | 出所 |
|---|---|---|
| 1 | 公式設問文（原文・字数条件込み） | `afternoonQuestionTexts` |
| 2 | 公式解答例 | `officialAnswers` |
| 3 | 配点 `{correct, partial}` | `scoringMap` |
| 4 | 採点基準（この設問が問う力点・本文の根拠・なぜその解答か・ありがちな失点） | `afternoonExplanations.rows[]` の `point`/`basis`/`reasoning`/`pitfall` |
| 5 | 問題の概要と本文セクション解説 | `afternoonExplanations.overview` / `detail.problemSections` |
| 6 | 利用者の解答（全行） | `myAnswers` |

`pitfall` は「ありがちな失点・誤答パターン」なので、**そのまま採点基準として効く**。
既存の解説データが期せずしてルーブリックになっている。

### 5.2 AI に禁止すること（プロンプトに明記）

- 模範解答と文言が違うだけで × にしない。**要素の一致で判定する**
- 逆に、もっともらしいが本文の根拠に基づかない解答を ○ にしない
- 配点を勝手に作らない。判定は ○/△/× の3値のみ（点数は `scoringMap` 由来でアプリ側が計算する）
- 書き直し例は**必ず設問の字数条件内**に収める
- 採点基準に無い独自の正解を持ち出さない

### 5.3 失点タイプの分類

午後Ⅰの失点は概ね以下に収まる。この分類が F3・F5 のアドバイスを駆動する。

| コード | 名称 | 説明 | 典型例 |
|---|---|---|---|
| `intent-miss` | 題意外し | 問われていることと違うことに答えた | 「事業面の狙い」と限定されているのに開発上の理由を書く |
| `evidence-missing` | 根拠不足 | 本文の記述に基づかず一般論・教科書的解答になった | 「適切にリスク管理する」 |
| `element-missing` | 要素不足 | 方向は合っているが必要な要素が欠けた | 「二つ挙げよ」に一つしか書かない／目的まで踏み込まない |
| `too-abstract` | 抽象度過多 | 具体性が足りず何を指すか特定できない | 「関係者と調整する」 |
| `length-violation` | 字数条件違反 | 指定字数の超過・不足 | 35字以内に要素を詰め切れない |
| `subject-mismatch` | 主語・対象ずれ | 誰が/誰に/何を、がずれている | 主体がPMなのに利用者を主語にした |
| `direction-wrong` | 方向性誤り | 根本的に別の解答 | — |

複数該当を許す（例: `intent-miss` + `too-abstract`）。

### 5.4 呼び出し方式

- **1問まるごと1リクエスト**（行ごとに分割しない）。設問間の関係を見て採点できるほうが精度が高く、レイテンシとコストも有利
- **構造化出力**（`output_config.format` のJSONスキーマ）で返させる。自由記述のパースはしない
- モデル: **Claude Opus 5（`claude-opus-5`）を推奨**。§9 R9 のとおり、誤採点は誤った学習を直接生むので、判断品質を優先する
- `thinking: { type: 'adaptive' }` を使う（採点は判断タスク）
- 実装は公式 SDK `@anthropic-ai/sdk` を使う（生の fetch は使わない）

## 6. アーキテクチャ

### 6.1 方式の比較

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A. Vercel Functions（推奨）** | `api/grade.ts` を追加。APIキーは Vercel の環境変数。ブラウザは自前の `/api/grade` を叩く | キーがブラウザに出ない。プロンプト・モデルをサーバ側で一元管理できる。将来 午後Ⅱ にも転用可 | エンドポイントが公開される→濫用対策が要る。関数のタイムアウト制約（§9 R11） |
| B. BYOK（ブラウザ直叩き） | 利用者が自分のAPIキーを設定画面に入力し、LocalStorage に保存してブラウザから直接 Anthropic API を呼ぶ | サーバ不要。アプリの「バックエンド無し」原則を維持できる | キーが LocalStorage に平文で残る。同期QRに乗せる/乗せないの判断も要る。ブラウザ直アクセスは本番用途として推奨されない |

**A を推奨する。** 理由は「キーを預けない」だけでなく、プロンプトと採点基準の作り方を
今後チューニングしていく以上、**サーバ側に置いたほうが改善サイクルが回る**ため。

### 6.2 構成（方式A）

```
ブラウザ (React)
  └─ POST /api/grade   { problemId, answers: {rowIndex: text}, elapsedSec? }
        │  ヘッダ: x-grading-key: <採点キー>
        ▼
Vercel Function  api/grade.ts  (Node ランタイム)
  ├─ 採点キー照合（環境変数 GRADING_SHARED_KEY）
  ├─ problemId から採点材料を組み立て（§5.1 の 1〜5）
  ├─ @anthropic-ai/sdk → claude-opus-5 構造化出力
  └─ 返却: AfternoonAiGrading (JSON)
```

- 採点材料（`officialAnswers` / `scoringMap` / `afternoonExplanations` / `afternoonQuestionTexts`）は
  **`src/data/` の既存ファイルを関数側からも import する**。二重管理しない
- 環境変数: `ANTHROPIC_API_KEY`, `GRADING_SHARED_KEY`（どちらも Vercel の環境変数。**コードに書かない**）

### 6.3 濫用対策

アプリの認証（`pmap:auth`）は**クライアント側だけの仕組み**で、
認証情報はバンドルに含まれている。したがって `/api/grade` をそのまま公開すると
**有料APIへの誰でも叩けるプロキシ**になる。対策:

1. **採点キー**（`GRADING_SHARED_KEY`）をサーバ側で照合。利用者は設定画面に一度だけ入力し、端末ローカルに保存
2. Anthropic コンソール側で**利用上限（spend limit）を設定**しておく（最後の防波堤）
3. リクエストサイズ・`problemId` の妥当性検証（既知の37問のみ受理）

> 採点キーはバンドルに含めない（ユーザが入力する）ので、認証と違って実際に秘密が保たれる。

## 7. データ設計

### 7.1 型（新規 `src/lib/afternoonAiGrading.ts` を想定）

```ts
export type AfternoonErrorType =
  | 'intent-miss' | 'evidence-missing' | 'element-missing'
  | 'too-abstract' | 'length-violation' | 'subject-mismatch' | 'direction-wrong'

export interface AfternoonAiRowResult {
  rowKey: string                 // '1|(1)|'
  rowIndex: number               // scorings のキーと一致
  judgment: AfternoonMarking     // 'correct' | 'partial' | 'wrong'（既存型を再利用）
  confidence: 'high' | 'low'
  summary: string                // 40字以内
  missing: string[]              // 不足要素
  errorTypes: AfternoonErrorType[]
  rewrite?: string               // 書き直し例（字数条件内）
  userOverrode?: boolean         // 利用者が最終的に別判定にしたか（記録時に確定）
}

export interface AfternoonAiGrading {
  version: 1
  model: string                  // 'claude-opus-5'
  gradedAt: string               // ISO
  problemId: string
  rows: AfternoonAiRowResult[]
  proposedScore: number          // AI 判定のみで計算した点（参考値）
  overall: {
    strengths: string[]
    weaknesses: string[]
    nextActions: string[]
  }
}
```

### 7.2 永続化

既存の `AfternoonSavedAnswerSnapshot`（`pmap:savedAnswers:<recordId>`）に
**任意フィールドとして追加する**。新しい LocalStorage キーは作らない。

```ts
export interface AfternoonSavedAnswerSnapshot {
  version: 1
  answers: AfternoonAnswerMap
  scorings: AfternoonScoringMap
  score?: number
  savedAt?: string
  aiGrading?: AfternoonAiGrading   // ★追加
}
```

理由:
- 記録の削除と一緒に消える（孤児データが出ない）
- **同期に自動的に乗る**（`LocalSyncState.savedAnswerSnapshots` が既に同期対象）
- 過去データは `aiGrading` 無しで正常に読める（`normalizeSavedAnswerSnapshot` に正規化を足すだけ）

### 7.3 同期の扱い

**同期対象とする。** 端末をまたいで弱点プロファイル（F5）が連続しないと意味がないため。
`savedAnswerSnapshots` 経由で既存の仕組みに乗るので、**`SYNC_SCHEMA_VERSION` の引き上げは不要**
（任意フィールドの追加で、旧バージョンは無視するだけ）。ただし実装時に旧端末→新端末の
マージで `aiGrading` が落ちないことを検証すること。

### 7.4 容量

- 1回分の `aiGrading` ≈ 3〜4KB（日本語 JSON）
- リスクレジスタ R4 で LocalStorage は既に 3〜4MB / 5MB を使用見込み
- 50回分で約 200KB。許容範囲だが、**`aiGrading` を持つ記録数の上限（例: 直近60件）を設け、
  古いものから `aiGrading` のみ削除する**方針を実装に含める（記録本体は消さない）

## 8. 非機能要件

| 項目 | 要件 |
|---|---|
| 応答時間 | 目標 60秒以内。フェーズ1で実測し、超えるならモデル/effort/分割を再検討（§9 R11） |
| コスト | §8.1。Anthropic コンソールで上限を設定する |
| 可用性 | AI が落ちていても演習・手動採点・記録は全機能が動くこと |
| 機密 | APIキー・採点キーをリポジトリに含めない。`.env*` を `.gitignore` に追加 |
| 対応幅 | モバイル375px と通常幅の両方。フィードバックが長いので折り畳みを活用 |
| 既存への影響 | `tracker` / `gamification` / `activityLog` / `sync` のスキーマを変えない |

### 8.1 コスト概算

1回の採点あたり（入力 約8,000トークン / 出力＋思考 約7,000トークン と仮定）:

| モデル | 単価(入/出 per 1M) | 1回あたり | 37問×3周=111回 |
|---|---|---|---|
| Claude Opus 5 | $5 / $25 | 約 $0.21（≒30円） | 約 $23（≒3,500円） |
| Claude Sonnet 5 | $2 / $10 | 約 $0.09（≒13円） | 約 $10（≒1,500円） |

**概算であり、フェーズ1で `usage` を実測して確定させる。**
差額は試験対策全体で約2,000円。判定品質を優先して Opus 5 を推奨する。

## 9. リスク

既存 `memory/risks.md` に追加すべきもの。

| ID | リスク | 影響 | 対応 |
|---|---|---|---|
| **R9** | **AI の誤採点による誤学習** | 間違った基準を身につける。R2（コンテンツ品質）の新しい形 | 判定根拠を必ず併記／利用者確認を必須化（F4）／確信度 low を明示／`userOverrode` を蓄積して精度を後追い検証 |
| **R10** | **APIキー漏洩・コスト濫用** | 金銭被害 | サーバ側のみに保持（方式A）／採点キーで入口を絞る／コンソールで利用上限 |
| **R11** | **Vercel Functions のタイムアウト超過** | 採点が常に失敗する | **フェーズ1の最優先検証項目**。超過時は ①ストリーミング応答 ②`effort` を下げる ③設問を2分割 の順で対処 |
| **R12** | IPA原文（設問文・解答例）を外部APIへ送信する | 著作権・運用上の判断 | 個人の学習目的の範囲だが、判断として明記。§12 で確認 |
| R4（既存） | LocalStorage 5MB 超過 | 学習履歴喪失 | §7.4 の上限・剪定方針を実装に含める |

## 11. 完了の判定条件

引継ぎ §7 の手順に加えて、本機能固有の条件。

1. `npx tsc --noEmit -p tsconfig.app.json` → エラー 0
2. `npm run validate-data` → `[OK] 全データの整合性確認完了`
3. `npm run lint` → src 配下 error 0
4. `npm run build` → 成功
5. Browser pane で 375px と通常幅の両方を実機確認。コンソールエラー 0
6. **AI採点が成功する経路**: 採点 → 行ごとのフィードバック表示 → `scorings` プリセット → 上書き可 → 記録 → XP加算 → 履歴に残る
7. **AI採点が失敗する経路**: オフライン／キー未設定／APIエラー のそれぞれで、**手動自己採点が従来どおり完走できる**
8. 既存の記録（`aiGrading` 無し）を開いても壊れない
9. 端末間同期で `aiGrading` が失われない
10. `git grep` で APIキー・採点キーの値がリポジトリに無いこと
